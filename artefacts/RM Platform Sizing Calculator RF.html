How these figures are derived

  • The latency budget sets how hard a pod may be driven. A looser p95 permits more queueing, so the autoscaler holds a higher CPU target and each pod serves more requests — but a pod's capacity is fixed by CPU, so the gain saturates. Four times the budget is nowhere near four times the throughput.
  • Application hosts hold the burst ceiling, or expected peak with one host down, whichever is larger. 16 cores to 64 GiB matches the services' own 500 millicore to 1 GiB request ratio, so neither dimension strands first.
  • Quantities of three or four are quorum and erasure-coding minimums, not load: etcd, RabbitMQ and Redis Sentinel need a majority; erasure coding needs four nodes to survive one loss.
  • Warehouse cores scale with the square root of read rate times row count, because columnstore scans parallelise across cores. Operational database cores scale with write rate, where connection handling and log flush dominate.
  • Every figure is a planning assumption. Confirm the bank's real concurrency profile and volumes in sprint 0, then validate against the service levels with a load test.

What each input does

Workload

InputWhat it meansWhat it changes
Provisioned usersHow many people have an account, whether or not they are using it right now — the size of the licence list.On its own, very little. What matters is how many are signed in at the same time, which is the next control.
Peak concurrencyOf those people, the share actually using the system at the busiest moment of the day.The most important input on this page. 10,000 users at 30% is 3,000 people at once, and nearly every figure here follows from that 3,000 rather than from the 10,000.
Customers (client entities)How many companies the bank banks.How much data there is: database size, cache memory, document storage. It barely touches the application servers, because a screen costs the same to draw whether the bank has 50,000 customers or 500,000.
Requests per active user per minuteHow busy one person is — screens opened, drill-downs, things saved. Twelve is someone working steadily, not hammering the keyboard.Multiplied by the concurrent users, this is the request rate the whole system has to carry.
Read share of trafficHow much of the work is looking things up, against changing them.Where the load lands. Reads are served by the warehouse and the cache; writes go to the operational database. Raising this shifts work from one to the other rather than adding it.

Performance targets

InputWhat it meansWhat it changes
API p95How long a screen is allowed to take. “p95” means 95 out of every 100 requests finish inside this time; the slowest 1 in 20 may take longer.How hard each server may be driven before it needs a neighbour. A looser limit means fewer servers — but the gain runs out around 2 seconds, because a server's capacity is set by its CPU, not by how long you are willing to wait.
Drill pageHow long opening a drill-down into underlying transactions may take.The data warehouse, and nothing else. That is where the large scans happen, and a longer allowance means each scan needs less parallel horsepower.
Message processingHow long a background event — a booking, a feed update — may sit before it is handled.The message broker alone. A longer allowance tolerates a deeper backlog, so fewer broker nodes are needed to drain it in time.
Cache hit rateHow often a repeated read can be answered from memory instead of going to the database.The sharpest of the four targets. At 80%, only 1 read in 5 reaches the warehouse. At 60% that doubles and puts the cores straight back onto it — which is why this is a target to engineer for, not to hope for.

Data volumes

InputWhat it meansWhat it changes
Postings per dayHow many transaction lines land each day.The size of the warehouse, together with the retention setting below.
History retainedHow far back the warehouse keeps transaction-level detail.Warehouse storage, almost directly — halve the months and you roughly halve the terabytes. Cores move far less, because a scan is bounded by the slice it reads, not by everything kept.

Availability

InputWhat it meansWhat it changes
AvailabilityWhether this is a production deployment that survives a server failure, or a pilot that does not.More than anything else on this page. Highly available means paired databases, quorum counts of three for the broker, cache and control plane, and a three-host application floor. Pilot means a single node of each. It is not half the size: dropping the readable standby puts the read path on the warehouse primary, which then needs about 30% more cores. What a pilot gives up is failover, the drill budget and the 99.5% target — so it is a way to try the product, not to run it.

Database engine

InputWhat it meansWhat it changes
Database engineWhich database the bank will run. It changes the engine named in every database row, the operating systems those servers support, and the software to install on them.The warehouse, through one thing: whether the engine has a columnar store. SQL Server Enterprise includes one. Oracle needs the separately licensed In-Memory option and PostgreSQL needs the Citus extension, so without those the same drill scans need about 1.5x the cores and the postings fact compresses about 1.8x less. Those two multipliers are planning estimates and want a benchmark. Oracle is not supported by the product today — see architecture/oracle-support-gap.md.

Pod and node sizing

InputWhat it meansWhat it changes
CPU request per podHow much processor each copy of a service reserves for itself. Everything in the application tier is counted up from this one number.The softest number on this page and the one with the most leverage. It has never been measured against a running service — it is a sensible starting guess. Dropping it from 500m to 300m takes the production pool from 5 hosts to 3. A load test is what settles it.
Memory request per podHow much memory each copy of a service reserves. The edge gateway is the exception at 512 MiB, because it holds no database connections.The memory side of the host pool. It rarely decides the host count, because these services run out of processor before they run out of memory — but set it too low and the JVM is killed under load.
Cores per application hostThe size of one server in the application pool. Memory follows at four times the cores.Server count and total cores, in opposite directions. Many small hosts waste cores on per-host overhead; few large ones waste them on the three-host minimum and lose more capacity when one fails. Around 12 to 24 cores is usually the sweet spot.

Deployment and scope

InputWhat it meansWhat it changes
With / without KubernetesWhether the services run on Kubernetes, which starts and stops copies by itself as load moves, or as ordinary programs on a fixed set of servers.Without it you must buy for the busiest moment of the day and leave it running all day, so the application tier grows by about a quarter. Total cores come out much the same; what you lose is automatic scaling, self-healing and rolling release.
EnvironmentsWhich of the three sets of hardware to count: the test environment, the live site, and the standby site.Everything, proportionally. Each is a complete environment in its own right.
Size UAT for load testingMakes the test environment large enough that a load test run there tells you something about the live site.Adds application hosts and warehouse storage to UAT. Without it, UAT proves the software works, not that it performs.
On-premises model servingWhether the AI features run on the bank's own GPUs instead of calling an approved outside service.Adds two GPU servers per site. Choose it when the bank will not allow any traffic to leave the data centre.
Bank already operatesTick each capability the bank already runs — load balancers, object storage, monitoring, backup, and so on.The biggest single lever on server count, and it costs nothing. Ticked lines drop out of the total, because the product connects to what the bank has instead of asking for another one.
